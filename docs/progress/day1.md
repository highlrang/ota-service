# Day1
## 설계
### 작업내용
도메인 정보를 수집 분석하여 핵심 도메인 모델을 도출한다.

### 의사결정
1. 내부 OTA 공통 도메인 모델을 기준으로 Extranet/Supplier 상품 DB를 통합한다
   - 고객은 상품의 유형과 상관없이 일관된 검색/예약 경험을 기대하기 때문이다
   - 또한 중복 등록된 숙소 제거와 재고 일관성 확보를 위해서도 도메인 모델 통합이 필요하다고 판단된다
   - Extranet과 Supplier의 상품DB가 통합된 DB를 관리하고, 상이한 정보에 있어서는 우선순위를 타입별로 구분하여 관리한다

2. 케이스에 따라 Supplier 연동 방식 채택하여 상품 DB의 품질을 향상시킨다
   - Real-time API : 실시간으로 숙소 상세 정보를 조회 가능한 API다
     - 고객이 숙소 상세 데이터를 조회할 때는 데이터를 정확도를 높여야하기 때문에 Real-time API를 사용한다
   - Webhook : Supplier 숙소 관련 변경에 따른 실시간 이벤트 수신
     - 숙소 DB 변경 내용을 실시간성으로 효율적이게 반영하기 위해 Push 방식의 Webhook을 연동한다
   - DB Cache API
     - 주기적 Polling 방식으로 상품DB를 업데이트하여 Webhook으로 처리되지 못 한 케이스를 보완해 데이터 정합성을 높인다

3. 가격과 재고 도메인을 분리한다
   - 가격과 재고는 객실 종류와 날짜에 따라 값이 변할 수 있다는 공통적이지만
   - 가격의 경우 재고와 다르게 인원 조건이나 프로모션에 따라 변동 가능하기 때문에 하나의 객실에 가격과 재고의 단위가 달라진다

4. 결제와 환불 도메인 분리
   - 결제와 환불은 예약과 연동되고 사용자 요금 및 결제 정보라는 점이 공통적이지만 
   - 결제는 예약 확정 시점에 발생하고 환불은 취소 시점에 발생한다는 시점의 차이가 있다.
   - 환불은 취소 정책과 환불 규칙에 따라 금액이 달라질 수 있기에 결제와 별도의 도메인으로 구분하여 히스토리를 남기는 것이 필요하다.
