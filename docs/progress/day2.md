# Day2
## 설계
### 작업내용
수집한 도메인 모델을 바탕으로 상태/코드 정의 및 Database Schema를 설계한다.

### 의사결정
1. 사용자 테이블 관리
   - Extranet 판매자 계정은 고객 사용자와 역할이 다르므로 `USERS`와 분리하여 `SELLERS` 테이블로 관리한다
2. Extranet, Supplier로부터 유입된 상품 정보는 Accommodations 테이블 하나로 관리한다. 
   - 상품 목록 조회 시 두 가지 유형 상품을 병합할 필요 없이 효율적으로 조회할 수 있도록 하기 위함
   - 여러 채널의 상이한 데이터를 관리하기 위해 `source_type`으로 출처를 구분하고 다음과 같이 컬럼 또는 별도 테이블로 관리한다
     - Extranet 상품은 `seller_id`를 통해 판매자 계정(`SELLERS`)과 연결한다
     - Supplier 상품은 외부 공급사에서 관리하는 상품 번호를 `external_product_id` 컬럼으로 관리한다
   - 외부 상품 번호는 현재 숫자 형태여도 향후 영문/특수문자 조합이 들어올 수 있으므로 정수형이 아닌 문자열 타입으로 관리한다
2. Accommodations 상세 설명 테이블 분리
   - 상세 설명은 길이가 길고 상품 목록 조회 시에는 필요하지 않으므로 별도의 테이블로 분리하여 조회 성능을 개선
3. Accommodations 이미지 테이블 분리
   - 이미지의 경우 Accommodations 테이블과 1:N 관계이므로 별도의 테이블로 분리한다
   - 다만 썸네일 이미지는 Accommodations 테이블에 저장하여 목록 조회 시 불필요한 조인을 방지한다
3. Region 테이블 추가 
   - 숙소가 위치한 지역의 정보는 계층 구조(시/도 - 시/군/구)로 이루어져있다
   - 숙소 검색 시 지역 선택 옵션을 제공하여 지역 아이디를 통해 숙소를 조회하는 경우에 사용된다 
   - 해당 데이터는 정적인 데이터이기 때문에 직관적인 계층 구조(parent_region_id, depth)로 관리하고 추후 성능 개선은 캐시를 활용한다
4. Reservation, Payment, Refund 테이블 분리
   - 장바구니가 존재하지 않고 여러 객실을 묶어서 예약하지 않은 객실 당 예약 하나 구조로 단순화하여 도메인 복잡도를 낮춘다
   - 예약에 대한 결제 및 환불은 처리 흐름과 데이터 단위가 다르기 때문에 별도의 테이블로 분리하여 관리한다
